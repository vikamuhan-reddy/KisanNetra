The always-on half of the sentinel, running as real firmware

Before building hardware, we wrote and ran the firmware for the pole's low-power microcontroller in the Wokwi ESP32 simulator: 12 sensor channels, a valve relay, a field display, fault injection and a live MQTT link. It makes the irrigation and alert decisions itself and keeps deciding with the network cut.

The circuit

What is wired to the ESP32, and what each part stands for

Wokwi has no soil probe, pH electrode or camera, so potentiometers stand in for those analog sensors; the firmware reads them exactly as it would read the real probe's voltage. Every analog input is on ADC1, because ADC2 pins stop working on the ESP32 while Wi-Fi is on.

Microcontroller

ESP32 DevKit v1
  • Validates every reading; an impossible value is treated as a fault
  • Keeps a 24-reading history for trends
  • Scores water, disease, pest, nutrient and flood risk
  • Decides locally, then publishes over MQTT if a link exists
  • Queues up to 50 records while offline

Verified behaviour

15 field situations, 15 correct decisions

The firmware's decision logic is pure Python, so a test harness runs the same main.py on a PC through 15 field states. A second check confirms the code uses nothing MicroPython on the ESP32 lacks. Both pass. The harness has already caught one real bug: a waterlogged, rainy field was once reported as "all signals normal".

One design rule, as arithmetic

The camera cannot raise an alarm on its own

Disease risk from vision is confidence × 55, and the alert threshold is 60. Even a 100% confident camera reaches only 55. The alert needs the air to agree:

Conditions measured by the nodeCamera confidence needed for INSPECT ZONE
Humidity above 80% and temperature 26–34 °C0.48
Humidity above 80% only0.70
Temperature in band only0.88
Neithernot reachable, capped at 55
90-second walkthrough

What to do in the simulator, and what happens

Let it runThe display cycles five pages; the green EDGE heartbeat blinks.
Turn the root-moisture knob (2nd from left) below 20%IRRIGATE NOW: the relay closes and the VALVE LED lights, with the reasons listed.
Click the HC-SR04 and set distance past ~43 cmTANK REFILL: the valve shuts rather than run the pump dry.
Restore the tank, press RAINDELAY IRRIGATION: it won't irrigate while rain is falling.
Press NETDisplay shows CLOUD:DN, records queue, and decisions carry on. Press again to replay the queue.
Press FAULT once, then againStuck probe, then failed probe: MANUAL CHECK both times, and no value is ever made up.
Set DHT22 humidity above 80%, turn the vision knob (far right) past ~0.5INSPECT ZONE: disease corroborated by humidity. Darken the light sensor and the alert drops.
Connectivity

Decides first, talks second

  • The first decision is made and displayed before the radio is touched. An earlier version waited ~12 s for Wi-Fi first; that was fixed.
  • Wi-Fi has an 8-second timeout and retries every 30 s; if it never comes up, the node runs anyway.
  • Offline records queue locally, capped at 50 (oldest dropped first, as real storage would).
  • The AI tier's result arrives on one interface: a potentiometer in the demo, MQTT here, UART on the real board.

MQTT topics (public HiveMQ demo broker)

sih26180/sentinel-01/telemetry   → sensor state, faults, trend
sih26180/sentinel-01/decision    → advisory, reasons, risks, valve
sih26180/sentinel-01/vision      ← AI result, e.g.
                                   {"disease": 0.85, "pests": 6}

A public, unauthenticated broker is fine for a demo; a deployed fleet needs per-device credentials and TLS.

Limits

What this simulation is not

  • Not field measurements. Readings come from knobs and clickable sensor parts; sensor drift and calibration error are not modelled.
  • No vision runs on the ESP32. Disease confidence is an input, as it will arrive from the Qualcomm QCS6490 tier over UART.
  • Not Qualcomm hardware. This is the low-power ESP32 tier; Qualcomm integration is the next phase.
  • N/P/K are derived from EC, exactly as low-cost "NPK sensors" do, labelled as a proxy, and never used to prescribe fertiliser.
  • Water flow is modelled in firmware; Wokwi has no flow-meter part. Thresholds are general starting points, not calibrated field constants.
